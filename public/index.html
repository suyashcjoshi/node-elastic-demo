✈ Skyward
Elastic Observability demo
🔍 Kibana investigation guide — 3 reveals, ~5 minutes
▼
Run a search, then follow these steps in Kibana while traces arrive. Each step uncovers one antipattern. Flip the matching flag in .env to fix it and watch the metrics change in real time.
1
Open the trace waterfall
Observability → Services → skyward-search → Transactions → click GET /api/search → open the slowest sample trace.
Look at the waterfall: four partner HTTP spans are lined up as a staircase — each waits for the previous to finish.
Reveal 1 · flip CHAOS_STAIRCASE=false
2
Check event-loop delay + /health latency
Observability → Services → skyward-search → Metrics tab. Find nodejs.eventloop.delay.p99 — spikes of 700 ms+ appear on every search.
Then Observability → Logs Explorer, filter url.path: /health — even the health endpoint shows the same delay. A blocked event loop hurts all requests.
Reveal 2 · flip CHAOS_GAP=false
3
Find the zombie partner in Service Map
Observability → Service Map — localhost:4004 (Zephyr) will be visibly hotter than the other three partners (higher error rate, extreme p99).
Click it → open an error trace → switch to the Logs tab inside → see partners_responded: 3 in the correlated pino log line.
Reveal 3 · flip CHAOS_PARTNER=false
4
Side-by-side comparison
Run npm run start:fast in a new terminal (port 3001, all chaos off, service name skyward-search-fixed). Both services appear in the APM service inventory simultaneously — compare latency distributions and event-loop metrics in the same time window.
Bonus · search http://localhost:3001 for the fixed experience
